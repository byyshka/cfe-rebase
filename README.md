# cfe-rebase

Переносит расширения 1С:Предприятия (CFE) на новый релиз типовой без Конфигуратора. Работает с XML-выгрузками на
диске и показывает, какие методы перехвачены и что вендор в них поменял. `&ИзменениеИКонтроль` и копии `&Вместо`
переносит трёхсторонним слиянием и доказывает, что контроль платформы пройдёт. Проверяет сигнатуры, вызовы и запросы.
Механику делает детерминированное ядро, человеку или нейросети остаются смысл и конфликты.

**Проверено на четырёх реальных базах УТ при переходе с 11.5.22.159 на 11.5.27.79.** Все четыре переноса шли через
оркестратор Hermes Agent с воркерами Claude Code. Экономным такой прогон не назовёшь, зато в авто-режиме он проходит
гладко и в фоне. Метаданные воркеры сверяли ещё и по графам старого и нового релиза (MCP-серверы на Neo4j); самому
пакету графы не нужны.

Запускается из командной строки (отчёты в JSON и Markdown) или как MCP-сервер для нейросетей — `cfe-rebase mcp`,
раздел ниже. Из командной строки нейросеть не нужна вовсе. Как MCP-сервер пакет проверен только с Claude Code:
протокол стандартный (stdio), но размер ответов и порядок работы в инструкции сервера подбирались под него.

Версия 0.3.4: ядро, CLI, MCP-сервер, реестр баз, план адаптации, проверки заимствований, чтения регистров, имён
форм и рабочей копии, правка заимствований. Что доказано на переносах УТ и 218 расширениях ERP 2.5, а где есть оговорки — в `docs/VALIDATION.md`.

Требования: Python 3.12+, `git` в `PATH` (трёхстороннее слияние — `git merge-file`). Сторонних зависимостей у ядра
нет; MCP-серверу нужен extra `mcp`. Платформа 1С пакету не нужна: он читает только файлы.

## Что нужно на входе

XML-выгрузки на диске, сделанные штатно: Конфигуратор → «Конфигурация» → «Выгрузить конфигурацию в файлы»
(проверено на выгрузках платформы 8.3.27, формат 2.20).

| Выгрузка | Что это | Аргумент |
|---|---|---|
| old | конфигурация, под которую написаны расширения, — обычно типовая прежнего релиза | `--old` / `--config-old` |
| new | типовая нового релиза | `--new` / `--config-new` |
| ext | расширения до переноса: папка с подпапкой на каждое расширение (или одна выгрузка расширения) | `--ext` / `--ext-root` |
| work | необязательно: уже перенесённые расширения — для сверки (`control-rebase`) и проверки перед загрузкой (`lint`) | `--work` |

Расширение из командной строки выгружается так:

```
1cv8.exe DESIGNER /S <сервер>\<база> /N <пользователь> /P <пароль> /DumpConfigToFiles "<папка>\<Имя>" -Extension "<Имя>"
```

Выгрузки пакет не меняет. Пишет он в папку отчётов `--out` (внутри выгрузки — отказ); `applied` — копии модулей в
`--dst` вне выгрузок; `prepare` запускает команду выгрузки расширений из реестра и создаёт рабочую копию расширений под
git, а MCP-инструмент `apply_candidate` пишет в неё (и только в модули, которые отслеживает git). Загрузить
перенесённое расширение в базу и пройти штатную проверку применимости — по-прежнему в Конфигураторе.

## Быстрый старт на синтетике

Из корня клона:

```
python -m pip install -e .
cfe-rebase control-rebase --ext tests/corpus/synthetic/ext --old tests/corpus/synthetic/old --new tests/corpus/synthetic/new --out <папка>
```

В консоли — сводка (15 методов: 9 REBASED, 1 CONFLICTS, …), в `<папка>/report.md` — разбор по методам, рядом —
кандидаты перенесённых методов. Карта случаев корпуса — `tests/corpus/synthetic/README.md`.

## Порядок работы

Предусловия: выгрузки в файлы (Конфигуратор → «Выгрузить конфигурацию в файлы») — расширения базы, по папке на
расширение, и типовая конфигурация старого и нового релиза; Python 3.12+ и `git`; для работы через агента — MCP-клиент
(проверено с Claude Code). Выгрузку расширений, с которой начат перенос, не перевыгружают: она — состояние «до», по
нему сверяется результат (в реестре — `proof_corpus: true`, тогда `prepare` выгрузку отклонит).

1. `prepare` — выгрузка, рабочая копия под git, восемь отчётов и план адаптации: «исправить» (что сломало обновление),
   «проверить», «уточнить». Начинать с «исправить».
2. Перенос по пунктам плана: `method-diff` — что вендор изменил в перехваченном методе; `&ИзменениеИКонтроль` —
   `control-rebase` (MCP `rebase_control` + `apply_candidate`), копии `&Вместо` — `merge-copy` (`port_replace`, слитое
   тело — `apply_candidate` по `copy_lines`);
   заимствования удалённых вендором объектов и объектов, которые вендор переименовал (`OBJECT_REMOVED` /
   `OBJECT_RENAMED` в `borrowed`), — `borrow-edit` (`apply_borrow_edit`).
3. Перед загрузкой — шесть проверок рабочей копии против нового релиза: `control-rebase --ext <рабочая копия>`
   (`check_control`: каждый метод `pass`), `calls`, `queries`, `borrowed`, `registers` (рабочая копия как
   `--ext-root`) и `lint` (`check_work`: ошибок 0); копии `&Вместо` — `bodies` (MCP `check_copies`, рабочая копия как
   `ext_root`: каждая копия `pass`). Рядом с `queries` и `registers` — `reads` (`check_reads`): в шесть
   проверок и в `prepare` не входит, вердиктов не даёт. Это регистры, которые расширения читают в запросах, а новый
   релиз изменил их состав или регистраторы: запрос компилируется, `queries` молчит, а цифры могут стать другими —
   данные таких регистров сверяют на обеих базах. Запускать до переноса по выгрузке расширений и перед загрузкой по
   рабочей копии. Там же — `names` (`check_names`, рабочая копия как `ext_root`): имена формы вендора, которые читает
   код заимствованных форм (`Элементы.X`, `Объект.X`, `Параметры.X`, реквизиты формы и переменные модуля), против
   `Form.xml` old и new; `GONE_IN_NEW` — исправить до загрузки; `LIST_QUERY_FIELD_MISSING` — запрос динамического
   списка, подменённый расширением, без поля, которое нужно форме вендора new, — тоже.
4. Загрузка в базу и приёмка — вне пакета (Конфигуратор или пакетный режим).

Не видно инструменту: собственные копии СКД и макетов вендора под другим именем, запись в регистр через
`ЗаполнитьЗначенияСвойств` или структуру — это сверяют по тексту.

Как это проверялось: команды пакета — прогонами по выгрузкам четырёх переносов УТ 11.5.22.159 → 11.5.27.79 (результат
сверялся с итоговыми расширениями этих переносов) и 218 расширений ERP 2.5 (`docs/VALIDATION.md`). Сами переносы шли
этим порядком через агентов: оркестратор Hermes Agent вёл этапы и запускал headless-воркеров Claude Code
(`claude -p`), правки в рабочую копию шли только по карточкам, которые утвердил владелец, загрузку в базу и приёмку
делал Claude Code в интерактивной сессии; три переноса прошли так до загрузки в базу, один был пробным прогоном на
уже сделанном переносе. В первых трёх воркеры работали со скриптами-предшественниками пакета или его CLI, четвёртый
прошёл через MCP-сервер 0.2.10.

## Установка

Для разработки — из клона репозитория, команда `cfe-rebase` появляется в `PATH`:

```
python -m pip install -e <путь к клону>
```

Одним файлом без установки — zipapp собирается из исходников и запускается любым Python 3.12+:

```
python scripts/build_pyz.py
python dist/cfe-rebase.pyz <команда> [аргументы]
```

`python -m cfe_rebase` делает то же, что `cfe-rebase`. Тесты: `python -m unittest discover -s tests -t .` из корня после
`pip install -e` (без установки — с `PYTHONPATH=src`).

Windows: пути синтетического корпуса доходят до 175 символов, и в глубокой папке `git clone` не развернёт файлы
(«Filename too long»). Клонируйте в короткий путь (`C:\src\cfe-rebase`) или один раз включите длинные пути:
`git config --global core.longpaths true`.

## Команды

`cfe-rebase <команда> --help` — аргументы команды, `cfe-rebase` без команды — список. Пути к выгрузкам типовой
(`--config-old` / `--config-new`, `--old` / `--new`) проверяются до анализа: папки нет или в ней нет ни одной
папки объектов (`Catalogs`, `Documents`, `CommonModules`, …) с XML объекта — один `Configuration.xml` не в счёт —
команда останавливается с текстом (MCP — `bad_input`), а не выдаёт отчёт,
в котором «ничего не нашлось».

| Команда | Что делает |
|---|---|
| `interceptors` | реестр перехватов расширений против нового релиза и мёртвый код расширений; перехват метода, который вендор пометил устаревшим (`TARGET_DEPRECATED`), и такого, который код вендора в new больше не вызывает нигде (`TARGET_UNCALLED`) или на части путей (`CALLERS_LOST`) |
| `calls` | вызовы методов конфигурации из расширений: наличие метода и число параметров в новом релизе, вызов метода, устаревшего в этом релизе (`CALLS_DEPRECATED`), вызов в модуль заимствованного объекта, который вендор удалил или переименовал, — и собственного метода расширения там (`OWNER_REMOVED` / `OWNER_RENAMED`); у вызова внутри копии `&Вместо` / `&ИзменениеИКонтроль` — уйдёт ли он пересъёмкой копии и как его теперь вызывает вендор |
| `bodies` | замороженные копии `&Вместо` против тела метода в старом и новом релизе: изменения вендора old→new, которые уже в копии (`in_copy`), и основа копии по ним (`new`, `mixed`, `old`, `older`); копия и обработчик события заимствованной формы, назначенный в `Form.xml` с `callType="Override"` без `ПродолжитьВызов` (`binding: callType`, вид «Вместо (callType)», цель — обработчик события в форме вендора) |
| `queries` | тексты запросов, схемы СКД и имена метаданных в строках против нового релиза |
| `merge-copy` | перенос одной копии `&Вместо` на тело нового релиза трёхсторонним слиянием; конфликты из одних пробелов разрешаются, вставки в одной точке помечаются; блок автора под другими условиями (`AUTHOR_BLOCK_MOVED`), вынесенное вендором тело (`BODY_EXTRACTED`); обёртку с `ПродолжитьВызов` не сливает |
| `control-rebase` | перенос всех `&ИзменениеИКонтроль` на новый релиз с проверкой контроля платформы |
| `method-diff` | что вендор изменил в каждом перехваченном методе (и в обработчике формы, заменённом `callType="Override"` без `ПродолжитьВызов`): блоки с номерами строк; вынесенное тело (`body_extracted`) |
| `hygiene-added` | эвристики гигиены кода только по добавленным строкам |
| `ext-check-diff` | разница двух прогонов расширенной проверки модулей |
| `applied` | применённая копия модуля: блоки `#Удаление` и строки маркеров опустошены, номера строк как в файле |
| `borrowed` | заимствованные объекты расширений против нового релиза: удалённые объекты, реквизиты, колонки табличных частей, ресурсы, значения перечислений, формы, сменившиеся типы; динамический список заимствованной формы, новый запрос которого не выбирает поле расширения |
| `registers` | запись в регистры (`СоздатьМенеджерЗаписи`, `СоздатьНаборЗаписей`; `Движения.<Имя>` — любое обращение), у которых новый релиз изменил измерения: новые измерения, имени которых (`.Имя`) нет в тексте метода, и удалённые поля, которые в нём есть; регистр, который вендор удалил |
| `reads` | регистры, которые расширения читают в текстах запросов (модули, `<QueryText>` динамических списков с ручным запросом, наборы данных СКД), а новый релиз изменил их состав (измерения, ресурсы, реквизиты, типы — в том числе через определяемый тип и у поля, перешедшего в другую часть), свойства, от которых зависит результат запроса (вид регистра, периодичность, режим записи, «использовать в итогах» у измерения), или регистраторы; регистр, который вендор удалил. Справочно, без вердиктов: запрос компилируется и `queries` молчит, а цифры могут стать другими. Чтение через менеджер в коде (`РегистрыНакопления.X.Остатки()`) и динамический список с одной основной таблицей без своего запроса не видит |
| `names` | имена формы вендора, которые читает живой код модулей заимствованных форм (раздел ниже): `Элементы.X`, `Объект.X`, `Параметры.X`, `ЭтотОбъект.X` / `ЭтаФорма.X` и имена без квалификатора, которые в old были реквизитами формы или переменными модуля, — против `Form.xml` вендора old / new, переменных модуля, метаданных объекта и добавлений самого расширения: `GONE_IN_NEW`, `NOT_IN_VENDOR`, `XML_UNREADABLE` |
| `lint` | рабочая копия перед загрузкой в базу: маркеры слияния, структура модулей, кодировка `.bsl` / `.xml`, потерянные файлы, BOM и концы строк; объект, переименованный в рабочей копии (тот же uuid объекта под другим именем), — одна находка `OBJECT_RENAMED`, его файлы сверяются под новым путём |
| `borrow-edit` | правка заимствований в рабочей копии (раздел ниже): снять заимствование (`--remove`) или переименовать его под новое имя вендора (`--rename`); `--dry-run` — только план |
| `prepare` | подготовка базы из реестра к адаптации: выгрузка расширений, рабочая копия под git, восемь отчётов и план адаптации |
| `select` | выборка из готового отчёта проверки (`calls`, `queries`, `borrowed`, `reads`, `registers`, `names`, `interceptors`, `lint`) без нового прогона: фильтр по модулю, объекту, флагу и уровню, сравнение с отчётом прошлого прогона (`new` / `kept` / `gone`), принятые находки; раздел «Выборка» ниже |
| `mcp` | MCP-сервер (stdio) поверх команд анализа и переноса из таблицы MCP ниже (без `hygiene-added`, `ext-check-diff`; правила `select` — параметры выборки у проверок): короткие ответы со ссылками на отчёты |

Переименование вендором. Вендор, переименовывая объект, сохраняет его uuid (11.5.17 → 11.5.27:
`СверкаВзаиморасчетов` → `СверкаВзаиморасчетов2_4`, `ТипыДокументовEDI` → `УдалитьТипыДокументовEDI`). Поэтому
заимствованный объект ищется в выгрузке типовой по `ExtendedConfigurationObject`, а в рабочей копии — по собственному
uuid объекта расширения: `borrowed` выдаёт `OBJECT_RENAMED` (и сверяет дочерние элементы с переименованным объектом),
`RENAMED` — у реквизита, измерения, ресурса, значения перечисления, табличной части; `interceptors` —
`TARGET_RENAMED` вместо `MISSING_BASE` и, после переименования заимствования, вместо `NEW_BASE`; `bodies`, `calls`,
`control-rebase`, `method-diff` берут модуль под именем объекта в своём релизе; `lint` — `OBJECT_RENAMED`. В плане
`prepare` такие находки — «исправить» с вызовом `borrow-edit`.

### `names`

Перехваты и копии в модуле заимствованной формы читают её элементы, реквизиты, параметры и переменные модуля по
имени: `calls` видит только вызовы, `borrowed` — реквизиты объекта, и имя, которое вендор убрал из формы в new, всплывало
только при загрузке (модуль не компилируется) или молча становилось локальной переменной. `names` берёт каждый модуль
формы с `<BaseForm>` в `Form.xml` расширения и собирает из живого кода (комментарии, строки и блоки `#Удаление` — нет):

| Что | Как в коде | С чем сверяется |
|---|---|---|
| `items` | `Элементы.X` (и `ЭтаФорма.Элементы.X`) | элементы `Form.xml`: всё дерево `ChildItems` с командными панелями, контекстными меню и подсказками |
| `attribute` | `ЭтотОбъект.X` / `ЭтаФорма.X` не вызовом; имя без квалификатора, которое в old было реквизитом формы или переменной модуля, а в методе не параметр и не `Перем` | реквизиты формы и `Перем` модуля формы вендора |
| `object` | `Объект.X` | реквизиты и табличные части объекта основного реквизита `Объект` (стандартные — `Ссылка`, `Номер`, … — не сравниваются) |
| `parameter` | `Параметры.X` | параметры формы (стандартные — `Ключ`, `ЗначениеКопирования`, … — не сравниваются) |

Вызовы (`X(…)`, `Элементы.Найти(…)`) — не сюда; квалификатор, который в методе параметр или `Перем`
(`Функция Ф(Знач Object)`), — не форма. Имя ищется в форме вендора old и new и среди добавлений расширения (то, что в его
`Form.xml` вне `<BaseForm>`, его `Перем`, его реквизиты объекта). Проверки:

- `GONE_IN_NEW` — в old было, в new нет, расширение само не добавляет: `error`; `risk`, если модуль формы new всё ещё
  называет это имя (`Элементы.X` или строкой — возможно, создаётся кодом). Поле `Объект`, переименованное вендором с
  тем же uuid, названо в `detail`; имя без квалификатора — там же: в new это локальная переменная метода.
- `NOT_IN_VENDOR` — имени нет ни в old, ни в new, ни в добавлениях расширения: `info` (создаётся кодом, чужое,
  опечатка); `risk`, если оно есть в `<BaseForm>` расширения — вендор убрал его ещё до old. Имена без квалификатора так
  не сообщаются.
- `XML_UNREADABLE` — `Form.xml` не разбирается, форма не проверена (`risk`).
- `LIST_QUERY_FIELD_MISSING` (`how` = `list`, `name` = `<Список>.<Поле>`) — расширение подменяет запрос динамического
  списка формы вендора: кодом (`<Список>.ТекстЗапроса` / `QueryText` = литерал, сцепление литералов или переменная,
  собранная из них в том же методе; `СтрЗаменить` с литералами применяется) или своим запросом `ManualQuery` в
  `Form.xml` (текст отличается от `BaseForm`), — а в запросе нет поля, которое нужно форме вендора new: `DataPath`
  элемента `<Список>.<Поле>` (английские имена стандартных реквизитов — `Ref`, `Date`, … — сверяются с русскими),
  поле `UseAlways` списка, чтение модуля формы new `Элементы.<Таблица>.ТекущиеДанные.<Поле>` (и через переменную
  метода) или `Элемент.ТекущиеДанные.<Поле>` в обработчике таблицы. Платформа молча убирает такую колонку, код вендора
  падает «Поле объекта не обнаружено». `error`, если форма old поле не требовала (его принёс релиз), `risk` — если
  требовала (колонки не было и до обновления); `needed_by` — где поле нужно, `new_in_new`, в `detail` — выражение
  вендора new для этого поля. Не сравниваются поля, которых нет и в запросе вендора new (их делает код вендора),
  `DefaultPicture`, запрос с `*` / `Таблица.*` (`Документ.Товары.*` — табличная часть, не мешает). Текст, собранный не
  из литералов (вызов функции, правка вендорского `ТекстЗапроса` через `СтрЗаменить`: поля вендора остаются), не
  судится — `summary.list_queries_unjudged`. В плане `prepare` — «исправить» (`error`) / «проверить» (`risk`).
  На реальных базах (11.5.22.159 / 11.5.17.172 → 11.5.27.79) находит, в частности, поле `ПредставлениеСостояния`
  списка формы `УправлениеОтгрузкой`, без которого код вендора падал «Поле объекта не обнаружено», и поля доставки
  (`ТребуетсяДоставка`, `ВидПланированияДоставки`, `СпособУказанияДоставки`), которые 11.5.27 добавил в `UseAlways`
  списков заказов и реализаций.
- `LIST_FIELD_NOT_LOADED` (всегда `risk`, в плане — «уточнить») — у такого списка расширение меняет и `UseAlways`
  (набор в его `Form.xml` отличается от `BaseForm`), а поле `UseAlways` вендора new, которое запрос расширения
  выбирает, не загружает ни `UseAlways` расширения, ни его видимый элемент (`DataPath` без `<Visible>false`). Если
  платформа берёт `UseAlways` расширения вместо вендорского, поля нет в данных строки — код вендора (видимость команд,
  `ТекущиеДанные`) его не получит. Заменяет платформа набор или сливает — не описано ни в документации, ни в
  спецификации выгрузки, по выгрузкам не доказать: `Form.xml` хранит полный набор в обеих частях, а `BaseForm`
  реальной заимствованной формы (`~Список.Ссылка`) не совпадает даже с old — поэтому `risk` и проверка в базе;
  `new_in_new` — поля не было в `UseAlways` old.

Форма, которой в new нет, — дело `borrowed` (`REMOVED`), здесь только счётом. На рабочей копии реальной базы УТ
11.5.17 → 11.5.27 (28 форм, 163 имени) `GONE_IN_NEW` нет; один `NOT_IN_VENDOR` risk — элемент общей формы, который
есть в `BaseForm`, а в 11.5.17 и 11.5.27 его нет (было и до переноса). С переставленными релизами (11.5.27 →
11.5.17) находит оба реквизита формы, которые 11.5.27 добавил и которыми пользуется рабочая копия.

### `borrow-edit`

```
cfe-rebase borrow-edit --work <рабочая копия> [--ext <расширение>] [--remove Вид.Имя …] [--rename Вид.Имя[=Новое] …]
                       [--config-new <выгрузка нового релиза>] [--dry-run] [--out <папка отчёта>]
```

Вид — по-русски (`Документ.Имя`), английским именем элемента (`Document.Имя`) или папкой (`Documents/Имя`).

- `--remove` — снять заимствование: XML объекта и его папка, строка в `ChildObjects` `Configuration.xml`, записи
  `<Metadata name="Вид.Имя…">` в `ConfigDumpInfo.xml` (вложенный блок целиком). Отказ, если код или XML расширения
  ссылаются на объект вне комментариев: `Документы.Имя`, `Документ.Имя` в тексте запроса, `ДокументСсылка.Имя`,
  `cfg:DocumentRef.Имя`, `Document.Имя.Attribute…`, вызов `Имя.Метод` общего модуля; ссылки перечисляются. Ссылки из
  объектов, которые снимаются тем же вызовом, не в счёт. Собственный (не заимствованный) объект — отказ.
- `--rename` — переименовать заимствование: файлы и папка объекта, его `<Name>` (если ещё старое), строка
  `ChildObjects`, записи `ConfigDumpInfo.xml` и английские ссылки в XML расширения (`cfg:DocumentRef.Имя`,
  `Document.Имя.Attribute.X`, `DocumentObject.Имя`). Русские ссылки — код BSL, тексты запросов в формах и макетах —
  перечисляются, но не переписываются: правятся руками. Без `=Новое` новое имя берётся из `--config-new`: объект с
  uuid из `ExtendedConfigurationObject` заимствования. Объект с новым именем уже есть — отказ.
- Все правки вызова планируются до записи: при отказе рабочая копия не меняется. Без `--dry-run` каждый файл, который
  меняется, перемещается или удаляется, должен отслеживаться git (откат — средствами git), переписываемый файл — быть
  в UTF-8. Файлы правятся строками и пишутся байт в байт: BOM и концы строк сохраняются, опустевшие папки удаляются.
- `--dry-run` — что удалится, переместится, изменится и какие ссылки найдены; рабочая копия не меняется. `--out` —
  `borrow_edit.json` / `borrow_edit.md` (вне рабочей копии). Код возврата: 0 — применено (или план без отказов), 1 —
  отказ, 2 — плохой вход.

Не видно: ссылки по имени в строке без вида (`РольДоступна("Имя")`, `Метаданные.НайтиПоПолномуИмени` с собранной
строкой). Проверено на рабочей копии реальной базы УТ (11.5.17 → 11.5.27): шесть снятых заимствований и три
переименованных документа дают дерево рабочей копии, байт в байт равное ручной правке того же.

## Реестр баз и `prepare`

Вместо четырёх абсолютных путей в каждом вызове — база и релиз:

```
cfe-rebase control-rebase --db demo-ut-27 --to 11.5.27.79
cfe-rebase prepare --db <база> --to <релиз>                   # выгрузка — только в новую папку задачи
cfe-rebase prepare --db demo-ut-27 --to 11.5.27.79 --no-dump  # эталон: proof_corpus в реестре
```

Пути берутся из реестра баз — JSON-файла: `--registry <файл>` (в MCP — `registry`), иначе переменная окружения
`CFE_REBASE_REGISTRY`, иначе `~/.cfe-rebase/registry.json`. Пакет читает из него только свои ключи, остальное
(строки подключения, пользователи, пароли) игнорирует и в сообщения не выводит; файл может быть общим с другими
инструментами.

```json
{
  "cfe_rebase": {
    "releases": {"11.5.22.159": "D:\\1c\\dumps\\UT_11_5_22_159", "11.5.27.79": "D:\\1c\\dumps\\UT_11_5_27_79"},
    "dump": "pwsh -File D:\\1c\\scripts\\dump-extensions.ps1 -DbId {id} -Names {names} -OutDir {dir}"
  },
  "databases": [
    {"id": "demo-ut-27", "aliases": ["demo"], "extensions": ["Доработки", {"name": "Печать", "src": "..."}],
     "cfe_rebase": {"from": "11.5.22.159", "task_dir": "D:\\1c\\tasks\\demo-ut",
                    "ext_dump": "before\\xml", "work": "work", "reports": "reports"}}
  ]
}
```

| Ключ | Смысл |
|---|---|
| `cfe_rebase.releases` | релиз → выгрузка типовой (old берётся по `from`, new — по `--to`) |
| `cfe_rebase.dump` | команда выгрузки расширений из базы — внешняя, пакет про платформу 1С не знает. Подстановки: `{id}` — id базы, `{names}` — имена расширений через запятую, `{dir}` — папка-родитель `ext_dump` (туда скрипт кладёт `xml\<имя>\…`). Шаблон делится на аргументы по пробелам, кавычки `"…"` группируют, `\` не экранирует; подстановка идёт внутри аргумента, поэтому путь с пробелами и кириллицей остаётся одним аргументом. Можно задать и списком аргументов |
| `databases[].id`, `aliases` | по ним ищется база (без учёта регистра) |
| `databases[].extensions` | имена расширений для `{names}`: строка или объект с полем `name` (прочие поля объекта не читаются) |
| `databases[].cfe_rebase.from` | релиз, под который написаны расширения базы; `--from` перекрывает |
| `databases[].cfe_rebase.proof_corpus` | `true` — `ext_dump` базы эталонный: `prepare` с выгрузкой отказывает (только `--no-dump`) |
| `task_dir` | папка задачи; `ext_dump` (по умолчанию `old\xml`), `work` (`work`), `reports` (`reports`) — от неё, абсолютные тоже допустимы |

Пути — с `\` или `/`, с `~`; относительные `releases` и `task_dir` — от папки реестра.

### `--db` у команд

`interceptors`, `calls`, `bodies`, `queries`, `borrowed`, `registers`, `reads`, `control-rebase`, `method-diff` принимают
`--db <id> [--to <релиз>] [--from <релиз>] [--registry <файл>]`. Пути, которых нет в командной строке, подставляются из
реестра: `--ext` / `--ext-root` — `ext_dump`, `--old` / `--config-old` — релиз `from`, `--new` / `--config-new` — релиз
`--to`, `--work` (только `control-rebase`) — `work`, если папка есть, `--out` — `<reports>/<команда>-<id8>/` (своя папка
на вызов, как у MCP: `control-rebase` и `method-diff` оба пишут `report.json`). Явно заданный путь перекрывает реестр.
`--to` обязателен, если не задан путь нового релиза. `lint` с `--db` берёт `--work` — `work`, `--ext` — `ext_dump`,
`--out` — из реестра, релиз ему не нужен. В конце сводки команда печатает `ext: <путь>, выгрузка от <время>` —
время самого нового файла выгрузки расширений: видно, не устарела ли она. Ошибка реестра — код 2 с текстом, какого
ключа нет.

### `prepare`

```
cfe-rebase prepare --db <id> --to <релиз> [--from <релиз>] [--registry <файл>]
                   [--no-dump] [--names a,b] [--only <имя>]
```

1. Пути из реестра; выгрузки типовой обоих релизов должны быть на месте (папки объектов с XML), иначе — какого релиза
   нет; у базы с `proof_corpus` без `--no-dump` — отказ; рабочая копия внутри выгрузки (или выгрузка внутри рабочей
   копии) — отказ. Проверяется до выгрузки: недостающий релиз не стоит минут Конфигуратора.
2. Без `--no-dump` — команда `cfe_rebase.dump` (без shell, stdin закрыт, вывод — во временные файлы, на всё
   `$CFE_REBASE_DUMP_TIMEOUT` секунд, по умолчанию 1800: дольше — команда и всё, что она запустила, снимаются, код 3; `--names` — выгрузить эти
   расширения вместо `extensions`). Код возврата ≠ 0 — стоп с командой и хвостом stderr. После выгрузки в `ext` должна
   быть хотя бы одна папка с `Configuration.xml`. С `--no-dump` берётся то, что уже лежит в `ext`.
3. Рабочая копия `work`: нет папки — копия `ext`, `git init`, `core.autocrlf=false` (выгрузка байт в байт: BOM, CRLF),
   коммит `before: <db> <from>`; автор — из конфигурации git, без неё — локально `cfe-rebase <noreply>`. Есть и под
   git — не трогается. Есть без git — стоп.
4. `control_rebase` (с `--work`, если рабочая копия была до этого вызова: свежую копию `ext` сверять не с чем),
   `interceptors`, `calls`, `queries`, `bodies`, `borrowed`, `registers`, `names` — в `<reports>/prepare-<run_id[:8]>/<инструмент>/`;
   `--only` — одно расширение.
5. План адаптации (`plan.json`, `plan.md` рядом): находки восьми отчётов (из `names` — только
   `LIST_QUERY_FIELD_MISSING` и `LIST_FIELD_NOT_LOADED`) сведены в пункты «расширение + модуль +
   метод» (для заимствований — объект) и разложены на **исправить** (что сломало или изменило обновление: перенос
   `&ИзменениеИКонтроль`, копия `&Вместо` с изменённым оригиналом, сигнатура, удалённый базовый метод, вызов или
   запрос, работавший в old, заимствованное поле, которое вендор удалил или перетипизировал, список формы, новый запрос
   которого теряет поле расширения, подменённый расширением запрос списка без поля, которое нужно форме вендора new,
   запись в регистр без нового измерения), **проверить** (дефекты,
   которые были и до обновления, и пункты в коде, который никто не вызывает или вызывают только из такого же кода:
   `caller_live` у вызовов, `method_live` у запросов и записей в регистры — «ссылок в расширениях нет» / «вызывается
   только из мёртвого кода»), **уточнить** (одна цель в нескольких
   расширениях, базовый метод появился только в new, заимствованное поле, которого нет ни в одном релизе), остальное —
   только счётом (DEAD_BINDING, DIRECTIVE_MISMATCH, изменения вендора под `&Перед` / `&После`, совместимые сигнатуры,
   вызовы устаревшего метода, который вендор сам вызывает в new).
   На трёх ручных переносах УТ человек менял 41 из 45 пунктов «исправить» (без заимствований), а из скрытого — только
   три `&После` рядом с другими пунктами. План не покрывает собственные копии СКД и макетов вендора под другим именем
   и запись в регистры через ЗаполнитьЗначенияСвойств или структуру.
6. Один экран: база, релизы, `ext` и время выгрузки, `work`, вердикты `control_rebase`, счёты всех отчётов, план
   (счёт по группам и пункты «исправить» с действием), пути к отчётам; те же данные —
   `<reports>/prepare-<run_id[:8]>/prepare.json`.

Код возврата: 0 — всё прогналось (конфликты переноса — находки, не ошибка), 2 — плохой вход (реестр, релиз, рабочая
копия без git), 3 — сбой выгрузки или git.

MCP: инструменты с `out` (`list_interceptors`, `method_diff`, `rebase_control`, `check_control`, `port_replace`,
`check_calls`, `check_queries`, `check_borrowed`, `check_registers`, `check_reads`, `check_copies`) принимают `db`, `to`, `from_release`, `registry` — пути тогда необязательны (`check_work` — только `db` и `registry`: релиз ему не нужен); в `inputs`
ответа — разрешённые пути, в конверте — `ext_newest`. У `port_replace` с `db` из реестра берётся `out`, а относительные
`old_module` / `new_module` / `copy_module` — пути внутри выгрузок old / new / ext. Инструмент `prepare(db, to,
from_release, registry, dump, names, only)` — то же, что команда:

```json
{"tool": "rebase_control", "arguments": {"db": "demo-ut-27", "to": "11.5.27.79"}}
{"tool": "prepare", "arguments": {"db": "demo-ut-27", "to": "11.5.27.79", "dump": false}}
```

## MCP-сервер

Тонкая обёртка над командами для нейросетей-оркестраторов: вместо чтения выгрузок и полных отчётов агент получает
короткий структурированный ответ — статус и классификацию машинными полями, по объекту на каждую единицу работы
(метод, находку), пути к полным отчётам, а тела методов и ханки — путём к файлу и диапазоном строк (номера строк — как
в настоящем файле). Транспорт — stdio, имя сервера `cfe-rebase`.

Размер ответа ограничен: `items` — до 20 тыс. символов JSON, `dead_code` — до 5 тыс. Длинный список обрезается:
строки отбираются по тяжести — у каждого инструмента свой порядок (ошибки, потом риски, потом справочное, уровни — в
разделе «Выборка»; у `method_diff` — сменившаяся сигнатура, потом изменённое тело; у `rebase_control` — не готовые
методы, потом `REBASED`; у остальных — строки с флагами, `fail` и находки «было корректно») — и отдаются в порядке
отчёта. Строка, которая одна больше бюджета (`method_diff` с `method` и длинными ханками), не выбрасывается, а
урезается: укорачиваются самые тяжёлые поля (у списка остаётся начало, у текста — начало с «…»), короткие — номера
строк, сигнатуры, флаги — остаются, что урезано — в её `trimmed`. В ответе тогда есть `truncated` (`total`,
`returned`, `trimmed`), полный список — в `report`, `summary` считает всё. `check_reads` отдаёт длинный составной
тип разницей (`added` / `removed`, `old_count` / `new_count`), первые 3 места чтения (`reads_total`) и первые 10 полей
места (`fields_total`), полностью — в `reads.json`. Без этого реестр перехватов двух расширений реальной
базы занимал 43 тыс. символов — больше порога предупреждения Claude Code (10 тыс. токенов), а с 50 тыс. символов
Claude Code переносит ответ инструмента в файл.

Установка — extra `mcp` (официальный MCP SDK; проверено на `mcp` 2.3.0, ядро от него не зависит):

```
python -m pip install -e "<путь к клону>[mcp]"
```

Запуск: `cfe-rebase mcp` (или `python -m cfe_rebase mcp`). Без установленного `mcp` команда печатает подсказку про
extra и выходит с кодом 2.

Регистрация в Claude Code:

```
claude mcp add -s user cfe-rebase -- cfe-rebase mcp
```

Произвольный клиент (stdio): command `cfe-rebase`, args `["mcp"]`, например

```json
{"mcpServers": {"cfe-rebase": {"command": "cfe-rebase", "args": ["mcp"]}}}
```

Все пути — абсолютные (или `db` и `to` — пути из реестра баз, раздел выше). `out` — папка для отчётов вне выгрузок: каждый вызов пишет в свою подпапку
`<out>/<инструмент>-<run_id[:8]>/`, выгрузки не пишутся (`out` внутри выгрузки — отказ).

| Инструмент | Команда | Что возвращает |
|---|---|---|

### Выборка: фильтр, «до/после», принятые находки

У `check_calls`, `check_queries`, `check_borrowed`, `check_registers`, `check_reads`, `check_names`, `check_work` и
`list_interceptors` — необязательные параметры (без них ответ прежний). Фильтр применяется до обрезки ответа;
`summary` считает все находки, как без выборки, а `summary.select` — что задано (`filter`) и что выбрано (`matched`,
`levels`; с `baseline` — `delta`, `baseline_findings`, `renamed_ext`; с `accepted` — `accepted`, `open`,
`accepted_unused`). Вся выборка без обрезки — `report.selection` (`selection.json` / `.md`: `key`, `level`, `delta`,
`accepted`, `finding`).

| Параметр | Смысл |
|---|---|
| `module` | подстрока места находки: путь модуля или файла от корня расширения, его имя (`Документ.X.МодульОбъекта`), метод; без учёта регистра, `\|` — или. У `check_reads` — по местам чтения: в строке остаются только подходящие места |
| `object` | объект метаданных целым сегментом имени: `Документ.X`, `X` или `Documents/X` — объект, в котором находка или о котором она (у `check_reads` / `check_registers` — и регистр) |
| `flag` | список флагов, проверок или `sev` — хватит любого: флаги `check_calls` и `risk` / `info` у `SIGNATURE_CHANGED`; `sev`, `kind`, `part`, `old` у `check_queries`; `check` у `check_borrowed`, `check_registers`, `check_reads`, `check_work` (и `severity`); флаги `list_interceptors` |
| `severity` | нижний уровень: `error` — только ошибки, `risk` — ошибки и риски, `info` — всё |
| `baseline` | прошлый прогон того же инструмента: отчёт (`<отчёт>.json` или папка с ним — подпапка вызова этого сервера, папка отчёта `prepare` целиком — берётся подпапка инструмента — или сама эта подпапка) или папка выгрузок расширений — тогда та же проверка с теми же `config_old` / `config_new` идёт по ней в `<подпапка вызова>/baseline` (у `check_work` — только отчёт). Каждой строке — `key` и `delta`: `new` (в baseline нет), `kept` (есть и там), `gone` (только в baseline: строка из него, в конце `items`; у отчёта без выгрузки пути относительные — `module` / `file`) |
| `accepted` | JSON-файл принятых находок: `[{"key": …, "reason": …}]` или `{"ключ": "причина"}`; строка с таким ключом получает `accepted` (причина) и в `open` не считается |

Уровни находок и ключи (ключ — поля без номеров строк через `|`, списки отсортированы и через запятую; одинаковые
ключи сопоставляются по одному):

| Инструмент | `error` | `risk` | `info` | Ключ |
|---|---|---|---|---|
| `check_calls` | `OWNER_REMOVED`, `OWNER_RENAMED`, `REMOVED`, `MISSING`, `NOT_EXPORT`, `TOO_FEW_ARGS`, `TOO_MANY_ARGS` | `SIGNATURE_CHANGED` risk, `CALLS_DEPRECATED` risk | `SIGNATURE_CHANGED` info, `CALLS_DEPRECATED` info (вендор сам вызывает метод в new) | `ext\|module\|caller\|call\|flags` |
| `check_queries` | `ОШИБКА?` | `РИСК` | `ПРОВЕРИТЬ` (внутри уровня первыми — «было корректно») | `ext\|file\|where\|part\|kind\|ref` |
| `check_borrowed` | `OBJECT_REMOVED`, `OBJECT_RENAMED`, `REMOVED`, `RENAMED`, `TYPE_CHANGED`, `LIST_FIELD_LOST`, `NAME_CLASH` | `XML_UNREADABLE`, `LIST_CHANGED` | `NOT_IN_VENDOR` | `ext\|object\|part\|name\|check` |
| `check_registers` | `REGISTER_REMOVED`, непустые `stale` или `key_lost` | остальное | — | `ext\|module\|method\|register\|check` |
| `check_reads` | `REGISTER_REMOVED` | `XML_UNREADABLE`; `CHANGED` с изменёнными измерениями, убранными ресурсами или реквизитами, сменившимися свойствами | остальное `CHANGED` | `ext\|register\|check` |

| `check_work` | `severity` = error | — | `severity` = info | `ext\|file\|check` |

Расширение, переименованное между прогонами (рабочая копия — `<имя>_<релиз>_<дата>_v_…`), считается тем же: по uuid
`Configuration`, когда обе стороны — выгрузки; иначе — если без пары с каждой стороны ровно по одному имени или текущее
имя начинается ровно с одного непарного имени baseline. Обрезка берёт строки так: открытые `new`, открытые `kept`,
принятые, `gone`, внутри — по уровню.

Пример «до/после» перед загрузкой: `check_calls(ext_root=[<рабочая копия>], …, baseline=<выгрузка до переноса>)` —
одним вызовом вместо двух прогонов и ручной сводки; `new` — то, что принёс перенос. Разбор по одному объекту без
нового прогона — CLI по отчёту `prepare`:

```
cfe-rebase select --report <reports>/prepare-<id>/calls --object Документ.ЗаказКлиента --severity risk
cfe-rebase select --report <out>/check_calls-<id> --baseline <reports>/prepare-<id>/calls --accepted accepted.json --out <папка>
```

`select` печатает по строке на находку (уровень, delta, accepted / open, ключ), с `--out` пишет `selection.json` /
`selection.md`; `--baseline` — только отчёт того же вида (файл или папка).

| `status` | `ok` или `error` |

| `inputs` | аргументы как переданы; с `db` — пути, разрешённые по реестру |
| `ext_newest` | с `db`: время самого нового файла выгрузки расширений |
| `summary` | счёты прогона |
| `items` | объекты-единицы: метод, находка, файл |
| `report` | `{json, md}` — пути к полным отчётам; с выборкой — ещё `selection` (`{json, md}` выборки без обрезки) |

| `truncated` | `items` / `dead_code` обрезаны по размеру: `{total, returned}` по каждому (`trimmed` — сколько строк урезано, а не выброшено) и `rest` — где полный список |

Port 1C:Enterprise configuration extensions (CFE) onto a new vendor release without the Designer. Works on XML dumps:
interception registry, vendor method diffs between releases, three-way rebase of `&ИзменениеИКонтроль` methods and
frozen `&Вместо` copies with a proof that the platform control passes, signature / call / query checks. CLI with JSON
and Markdown reports, plus an MCP server for LLM agents (`cfe-rebase mcp`, extra `mcp`); a registry of databases
replaces the paths (`--db <id> --to <release>`), and `prepare` dumps, sets up a git work copy, runs the checks and
merges them into an adaptation plan in one go; `borrowed` checks adopted metadata and adopted form lists against the
new release, `bodies` (MCP `check_copies`) whether each frozen `&Вместо` copy carries the vendor changes, `names`
the vendor form names adopted form modules read, interceptors and calls of methods the vendor made obsolete are
